# **Roadmap: критичный запуск на внешнюю аудиторию (S1)**

## **Цель**
- Вывести префлоп-тренажёр на внешнюю аудиторию сегмента `S1 (Новичок)` с рабочим продуктовым путём:
- `вход -> первый запуск -> тренировка -> ценность -> тариф -> оплата -> продолжение`.

## **Input**
- Есть беклог `001-011` по пути `S1`.
- Есть интервью и JTBD-гипотезы по новичкам.
- Есть набросок пользовательского пути в Figma.
- Не зафиксирован финальный объём платной ценности и точка апгрейда.

## **Output**
- Последовательность релизных работ по критичности зафиксирована.
- Для каждого пункта определён проверяемый результат.
- Понятно, что делается сначала, что можно запускать параллельно, что позже.

## **Outcome**
- Пользователь из внешнего трафика может пройти путь до первой ценности без ручного сопровождения.
- Появляется управляемый платёжный флоу и основа для внешнего масштабирования.
- Снижается риск провала запуска из-за незакрытых базовых сценариев.

---

## **Релизная последовательность (по критичности)**

### **1. Вход в продукт и первый запуск (must-have до всего остального)**
- `001` Страница входа в тренажёр и ценность для `S1`.
- `002` Авторизация и вход в тренажёрный flow.
- `003` Онбординг `S1` (что такое чарты, как тренироваться, как получить пользу).

**Критерий готовности**
- Новый пользователь без курса заходит с внешнего источника, регистрируется, понимает первый шаг и запускает тренировку.

### **2. Ядро тренировки и моментальная польза (must-have до платного апгрейда)**
- `004` Доступ к паку прямо в окне тренировки.
- `005` Мгновенный разбор ошибки после ответа.
- `008` Продолжение незавершённой тренировки.
- `009` Управление активной тренировкой при запуске новой.

**Критерий готовности**
- Пользователь не теряет сессию, быстро понимает ошибку и продолжает тренировку без разрыва сценария.

### **3. Упаковка предложения и доверие к продукту (must-have для конверсии)**
- `006` Витрина паков: общие и от команды Firestorm.
- `007` Блок про команду Firestorm и путь вступления через курс.

**Критерий готовности**
- Пользователь понимает разницу ценности: базовый контент vs экспертные паки Firestorm и почему это стоит покупать.

### **4. Монетизация и платёжный путь (must-have для внешнего релиза)**
- `010` Страница тарифов.
- `011` Интеграция оплаты и выбор эквайринга.

**Критерий готовности**
- Есть рабочий путь `попал в ограничение/ценность -> выбрал тариф -> оплатил -> получил доступ`.

---

## **Что делать параллельно**
- Параллельно с блоком `1-2`: финализировать механику paywall (по лимиту времени/раздач/сессий).
- Параллельно с блоком `3`: готовить тексты и UX тарифной страницы (`010`).
- Параллельно с блоком `4`: согласовать с разработкой и финансами shortlist эквайринга.

## **Что не откладывать**
- Решение по точке апгрейда для `S1` (когда именно показываем тариф).
- Формулировку платной ценности (что именно даём сверх бесплатного сценария).

## **Что можно отложить после первого внешнего запуска**
- Глубокая сегментная персонализация онбординга.
- Дополнительные способы входа сверх уже согласованных.
- Расширенные AI/аналитические сценарии, не влияющие на базовый путь оплаты.

---

## **План на день (фокус на внешнем запуске)**

### **1. Зафиксировать monetization decision**
- Определить точку апгрейда: по времени, по количеству раздач или по комбинированному лимиту.
- Зафиксировать минимальный состав платной ценности для `S1`.

### **2. Довести до согласования блок 1**
- Проверить связку `001 + 002 + 003` на цельный путь первого запуска.
- Подготовить короткий сценарий проверки: 1 новый пользователь -> 1 успешный запуск тренировки.

### **3. Довести до согласования блок 2**
- Зафиксировать UX-сценарий ошибок и продолжения сессии (`004/005/008/009`) как единый поток.

### **4. Подготовить вход в блок 4**
- Согласовать рамку тарифов (`010`) и требования к платёжному флоу (`011`) до постановки в разработку.
