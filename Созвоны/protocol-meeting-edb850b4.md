## Принятые решения

### 1. Организация работы в канбан-доске

**Решение:** Все задачи по тренажеру будут вестись в единой канбан-доске. Столбцы: Backlog (все известные задачи), Анализ/Дизайн (задачи, требующие уточнения перед разработкой), Selected (готовые к разработке), In Progress, Done.

**Обоснование:**
- Необходима единая точка истины для отслеживания прогресса.
- Разделение на этапы (анализ -> разработка) позволяет четко определить готовность задачи к передаче разработчику.
- Позволяет избежать путаницы, особенно при параллельной работе над тренажером и интеграцией с PH.

**Распределение ответственности:**
- **Саша Академик:** Курирование доски, простановка приоритетов, передача задач в разработку.
- **Александр Еленский:** Наполнение карточек в столбце "Анализ/Дизайн" необходимой информацией (скрины, примеры, логика).
- **Макс (разработчик, не на встрече):** Исполнение задач из столбца "Selected".

### 2. Подход к разработке интерфейса редактора чартов

**Решение:** В первую очередь Макс должен исправить критические функциональные баги и добавить базовый функционал (кастомные названия действий). Глубокий редизайн интерфейса редактора отложен на второй этап.

**Обоснование:**
- Текущие предложения по дизайну от непрофессиональных дизайнеров (не покеристов) были признаны неудобными для целевой аудитории.
- Необходимо иметь стабильную и функциональную версию продукта, прежде чем заниматься ее визуальной оптимизацией.
- Команда (Саша, Александр) сможет самостоятельно набросать необходимые правки по верстке после фикса базового функционала.

**Распределение ответственности:**
- **Макс:** Приоритетная реализация функциональных фич и исправление багов.
- **Саша Академик / Александр Еленский:** Формирование списка конкретных правок по интерфейсу редактора после стабилизации функционала.

### 3. Стратегия запуска и сбора метрик

**Решение:** Запустить лендинг для тренажера в ближайшее время (в апреле) для сбора первой обратной связи, не дожидаясь полной готовности всего функционала и онбординга.

**Обоснование:**
- Важно получить быструю обратную связь от реальных пользователей, чтобы выявлять проблемы и корректировать развитие.
- Запуск без агрессивной рекламы (на салон) позволит протестировать воронку и базовые метрики (клики, регистрации) с минимальными рисками.
- Полноценный запуск с рекламой планируется после реализации встроенного онбординга.

**Распределение ответственности:**
- **Никита Нагибин:** Подготовка финальной версии текстов для лендинга с учетом фидбэка.
- **Саша Академик / Александр Еленский:** Проверка текстов лендинга на предмет понятности для новичков.
- **Макс:** Техническая реализация и выкладка страницы на сайт PokerHub.

## Ключевые моменты обсуждения

### Организация работы и канбан

Обсуждена структура канбан-доски для управления задачами по тренажеру. Backlog для всех идей, столбец "Анализ/Дизайн" для задач, требующих уточнения (логика, примеры интерфейса), и "Selected" для готовых к разработке. Александр Еленский отвечает за наполнение карточек в "Анализ/Дизайн".

### Технические долги и приоритеты

Выявлен ряд критичных проблем: старый тренажер внутри курсов, баг с прогрессом при разрыве соединения, отсутствие кнопок перехода между режимами просмотра и тренировки. Задача переноса обновленного тренажера с Dev на Prod и в курсы признана самой ресурсоемкой.

### Ценность чартов Firestorm

Саша Академик объяснил, что чарты команды Firestorm — это эксплойт-чарты. Они строятся на анализе майнинга (миллионов раздач) для определения средней стратегии поляны, после чего рассчитывается контрстратегия. Эти чарты упрощены по сравнению с чистыми GTO-чартами для удобства игры, но остаются эффективными. Они дают фундамент, от которого игрок может отталкиваться, подстраиваясь под конкретных оппонентов или стадии турнира.

### Стратегия для новичков и монетизация

Обсуждена гипотеза о выходе на широкую аудиторию новичков, которые играют в покер от случая к случаю. Для них необходимо создать объясняющий онбординг и материалы, демонстрирующие базовую ценность чартов. Монетизация видится не в прямой конкуренции по цене подписки, а в увеличении DAU/MAU и последующей конвертации в контракты с командой Firestorm. Рассматриваются модели подписки и баланса (депозита).
